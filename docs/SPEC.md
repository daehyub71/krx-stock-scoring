## 1. 목표와 범위

매 거래일 KOSPI·KOSDAQ 종목을 빠짐없이 목록화하고, 기술·재무·공시·수급으로 **규칙상 종합 상태 점수**를 산출한다. 점수, 데이터 관측률, 위험 표지는 서로 다른 정보로 표시한다. 입력이 부족한 종목에 억지로 확정 점수를 부여하지 않는다.

### 1.1 제품 범위

- 개인용 웹에서 순위·항목별 실제 입력·결측·버전·자료 기준일을 조회한다.
- 모든 대상 종목은 `scored / provisional / insufficient_data / excluded` 중 하나의 상태로 남는다.
- 기존 alerts 신호와 점수의 관계를 기준 거래일·공개시각에 맞춰 비교한다.
- 점수 계산의 정확성·분포·안정성·재현성을 검증한다. 신호 자체의 검증은 `krx-signal-verify`의 책임이다.
- 자동매매, 가격 예측, 목표가·진입/청산 지시, 외부 알림, 실시간 호가, LLM 감성 분석은 이번 범위 밖이다.
- 이 문서는 SPEC이다. PLAN·TASK·애플리케이션 코드·운영 배포를 생성하거나 실행한 것으로 간주하지 않는다.

### 1.2 선행 프로젝트 경계

```text
charts: ksc_* ── 읽기 전용 입력 추출 ──┐
alerts: ksa_* ─ 기준일/생성시각 대조 ─┤
verify: 검증된 파서·픽스처 재사용 ────┤
                                      ▼
scoring: 입력 스냅샷 → 점수 계산 → 검증 → kss_* 게시본 → 개인 웹
```

- scoring은 `ksc_* / ksa_* / ksv_*`를 수정하지 않는다. `ksv_verdicts`는 선택적인 참고 표시이며 점수 입력에는 넣지 않는다.
- 상위 수집 결함을 scoring의 계산 방어로 피하는 것과 상위 결함 자체를 고치는 것은 별도 작업이다.
- charts 완료 이벤트를 보내는 상위 workflow 변경, DB 읽기 역할 부여, W/M 정리·백필은 별도 변경 범위다. 이번 문서는 해당 작업의 필요 조건만 정의한다.
- verify M9의 달력상 관찰 대기를 SPEC 작성의 포괄적 선행 조건으로 두지 않는다. 실제 재사용 모듈·권한·데이터 계약의 준비 여부로 착수 조건을 판단한다.

### 1.3 유니버스

약 2,770개는 과거 관측 규모이며 고정 정답이 아니다. 당일 유니버스 스냅샷의 종목 수를 사용한다. 티커는 숫자가 아닌 문자열이며 `^[0-9A-Z]{6}$` 계약을 검증한다.

| 대상 | 목록 | 기본 랭킹 정책 |
|---|---|---|
| KOSPI·KOSDAQ 일반 보통주 | 포함 | 일반기업 프로필, 자료·위험 조건 충족 시 참여 |
| 우선주·스팩 | 포함 | 제외 사유 표시, 기본 랭킹 제외 |
| 금융·보험·리츠 | 포함 | `special_sector`로 분리, 업종별 산식 검증 전 일반기업과 비교하지 않음 |
| 신규상장 | 포함 | 워밍업 부족 시 잠정/자료 부족 |
| 거래정지·중대 위험 종목 | 포함 | 위험 상태 표시, 일반 랭킹·등급 보류 |
| 외국법인 상장주 | 포함 | 통화·회계기간·DART 매핑 검증 실패 시 자료 부족 |
| KONEX·ETF·ETN | 범위 밖 | 향후 별도 프로필로 확장 |
| 상장폐지 | 과거 스냅샷 보존 | 당일 신규 랭킹 제외, 과거 검증에서 임의 삭제 금지 |

공식 분류를 우선한다. alerts의 우선주 코드 규칙·스팩 이름 규칙은 검증 가능한 보조 판별로 재사용한다. 이름 한 가지나 최근 10거래일 봉 부재만으로 상장폐지를 확정하지 않는다. 판별 근거가 부족하면 `classification_unknown / no_recent_bars`로 기록한다. 업종 빈값도 시장·종목 삭제로 숨기지 않는다.

### 2.2 M0의 첫 행동: 읽기 전용 점검

우선순위는 **1) 저장 용량 2) 배치 시점 3) W/M 잔류**다. 접근 가능해지면 저장 용량 조회와 아래 중복 조회를 같은 점검에서 먼저 수행한다. 스키마·열 타입을 확인한 뒤 조회하며 실제 결과와 실행시각을 기록한다.

```sql
-- 먼저 DB 크기. 서비스 할당량·청구 기준은 대시보드 값과 별도 대조한다.
SELECT pg_size_pretty(pg_database_size(current_database())) AS db_size;

-- 최근 구간에서 ticker별 같은 주/월의 행 중복 확인.
-- lower_bound / upper_bound는 점검 대상 거래일 범위로 변경한다.
WITH params AS (
  SELECT DATE '2026-08-01' AS lower_bound,
         DATE '2026-09-16' AS upper_bound
), periods AS (
  SELECT b.ticker, b.timeframe,
         CASE b.timeframe
           WHEN 'W' THEN date_trunc('week', b.d::timestamp)::date
           WHEN 'M' THEN date_trunc('month', b.d::timestamp)::date
         END AS period_start,
         b.d
  FROM public.ksc_bars AS b
  CROSS JOIN params AS p
  WHERE b.timeframe IN ('W', 'M')
    AND b.d >= p.lower_bound AND b.d <= p.upper_bound
)
SELECT timeframe, ticker, period_start, count(*) AS rows_in_period,
       min(d) AS first_d, max(d) AS last_d
FROM periods
GROUP BY timeframe, ticker, period_start
HAVING count(*) > 1
ORDER BY timeframe, period_start DESC, ticker;
```

특정 날짜 이후의 `count > 1`처럼 여러 주를 한데 묶는 판정은 사용하지 않는다. 반드시 주/월 기간별로 묶는다. 결과가 0행이어도 일봉과 집계 값의 일치까지 증명된 것은 아니다. 이 조회는 자료를 삭제·복구하지 않는다.

추가 점검: 시장별 D/수급/공매도 최근 40일 행 수, 중복·NULL·날짜 상한, 지수 달력과 독립 거래일 달력, 유니버스 갱신일, `ksc_meta`의 update/universe/drift, 테이블·인덱스 크기. 조회 결과 없이 M0를 완료 처리하지 않는다.

## 4. 점수 모델과 비교 자격 — F1~F9, F19

### 4.1 배점과 모델 버전

**v2.7 개정 (2026-09-20, 사용자 결정): 배당수익률을 기본 축에 더해 기본 36점 · 총점 100점으로 한다.** 기본 36 = PER 6 · PBR 5 · 영업이익률 7 · 성장률 6 · ROE 5 · 부채비율 3 · **배당수익률 4**. 배당수익률은 KRX 공표값(pykrx `DIV`)을 그대로 쓰고 근거에 `DPS`를 함께 남긴다 — 최근 결산연도 중간배당 포함 주당배당금 ÷ 현재가이며, 리츠는 KRX가 12개월 연환산으로 준다.

**v2.5 개정 (2026-09-20, 사용자 결정): 뉴스를 공통 점수에 넣는다.** 뉴스는 관련 기사 **3건 × ±3점 = −9 ~ +9**다. 신용 2점은 계속 비활성이므로 공통 원배점은 **100점**(기술 35 + 기본 36 + 공시 7 + 수급 13 + 뉴스 9, v2.7)이며, **환산 없이 원점수 그대로** 저장·표시한다. v2.0~v2.4의 「뉴스 8점 별도 보조·공통 90점」(V6)은 이 결정으로 대체됐다.

| 축/항목 | 공통 원배점 | 취급 |
|---|---:|---|
| 기술: 정배열 / 추세 / 거래량 / 가격대별 거래량 근사 / RSI·MACD | 11 / 6 / 6 / 7 / 5 = **35** | 공통 점수 |
| 기본: PER / PBR / 영업이익률 / 성장률 / ROE / 부채비율 / 배당수익률 | 6 / 5 / 7 / 6 / 5 / 3 / 4 = **36** | 공통 점수 (v2.7) |
| 공시 | **7** | 공통 점수 |
| 수급: 외국인 / 기관 / 공매도 거래 비중 | 6 / 5 / 2 = **13** | 공통 점수 |
| 뉴스 | **9** (−9 ~ +9) | 공통 점수 — 관련 기사 3건 × 호재 +3 / 악재 −3 / 중립 0 |
| 신용 | **2** | 모델 비활성, 종목별 missing 목록에 넣지 않음 |

공통 활성 항목은 **17개**, 비활성 신용 1개로 개념상 총 18개다. 완전 관측 종목의 `total`은 **원점수 그대로**(최대 100, 뉴스가 모두 악재면 음수 가능)이며 환산하지 않는다. UI는 `총점 X/100 (뉴스 ±9 포함)`으로 설명한다. 음수 총점을 0으로 자르지 않는다.

신용 도입처럼 모델이 다시 바뀌면 새 `scoring_profile / rules_version`을 만든다. v2.5의 뉴스 편입도 새 규칙 버전으로 올리며, 90점 모델의 점수와 같은 시계열로 잇지 않는다. 서로 다른 모델의 점수 변화·등급·순위를 같은 시계열로 조용히 연결하지 않는다.

### 4.2 규칙의 단일 기준 — F1

`rules/<version>.yaml`을 계산·검증의 단일 기준으로 둔다. `docs/RULES.md`는 해당 규칙에서 생성하거나 일치 검사를 거치는 설명서다. 코드와 문서에 독립된 상수 사본을 두지 않는다.

규칙에는 항목 ID, 원배점, 산식, 단위, 기간, 최소 관측 수, 임계값, 경계 포함 여부, 무효값 정책, 필수 입력, 비교집단, 반올림, 위험 정책을 포함한다. 정렬·직렬화 방식이 고정된 해시로 규칙을 식별한다.

**워크스페이스 밖 파일을 읽어야만 구현할 수 있도록 두지 않는다.** 원본 임계값(`idea_md/README.md`, `idea_md/krx-stock-scoring-plan-v1.0.md` §2.4)은 §4.5에 옮겨 적었고, 이 SPEC과 `rules/v0.yaml`이 기준이다. 원본에 없는 값(§4.5 표의 *보완* 표시)은 새 제안임을 밝히고 M1~M3에서 표본과 함께 확정한다. M6 검증 전 계산은 `experimental=true`이며 확정 등급을 게시하지 않는다.

### 4.3 입력 상태와 관측률 — F6

| `parts[].state` | 의미 | 점수/관측률 |
|---|---|---|
| `observed` | 유효한 실제 관측 | 계산 / 관측에 포함 |
| `no_event` | 정해진 범위를 완전히 조회했으나 관련 사건 없음 | 해당 규칙의 중립값 / 관측에 포함 |
| `adverse_defined` | 적자·자본잠식 등 불리한 상태가 입력으로 확인됨 | 정의된 불리 점수, 기본 0 / 관측에 포함 |
| `missing` | 값 부재·기간 부족·미조회·출처 실패·노후·잘못된 값 | 점수 null / 관측에서 제외 |
| `not_applicable` | 해당 프로필에 경제적으로 적용 불가 | 일반기업 프로필에서 임의 면제하지 않고 별도 프로필/보류 |

`missing_reason`은 `not_queried / insufficient_history / source_error / stale / invalid_value / unavailable` 등으로 세분한다. NULL과 실제 0, 거래 없음, 요청 실패를 구분한다. pykrx의 PER=0만 보고 적자라고 확정하지 않는다. 손실·자본 상태가 별도로 확인되면 `adverse_defined`, 뜻을 판별할 수 없으면 `missing`이다.

계산 정의:

```text
axis_available_max = 해당 축의 observed/no_event/adverse_defined 항목 만점 합
axis_coverage = axis_available_max / axis_model_max
coverage = 전체 available_max / 100
axis_estimate = axis_model_max × axis_observed_points / axis_available_max
estimated_total = sum(axis_estimate)   # 100점 척도 그대로
```

뉴스 항목은 음수(−9)를 낼 수 있다. 축 점수·총점·추정에서 음수를 0으로 자르지 않는다.

어느 축의 `axis_available_max=0`이면 `estimated_total=null`이다. 잠정 점수 표시의 초기 하한은 **전체 관측률 80%, 각 축 60%**다. 검증할 운영 기본값이며 수익 예측 신뢰도를 뜻하지 않는다. 하한 미달이면 총점·등급을 보류하고 관측된 항목만 표시한다.

**기본 랭킹은 공통 항목이 모두 관측된 동일 프로필 종목만** 참여한다. 80% 이상인 부분 관측 종목은 `provisional`로 추정치를 보여주되 기본 랭킹·확정 등급에서 분리한다. 잠정 종목을 별도로 비교할 때도 `availability_signature`가 같은 집단끼리만 비교한다. 하한을 통과했다고 결측 편향이 해결된 것으로 간주하지 않는다.

**점수 열의 뜻 (v2.8, 2026-09-20 사용자 결정)**

| 열 | 채우는 때 | 뜻 |
|---|---|---|
| `raw_total` | 관측 항목이 하나라도 있으면 **모든 상태에서** | 관측된 항목 점수의 합 (그 프로필 척도) |
| `profile_max` | 항상 | 그 프로필의 만점 — 중간 프로필은 100이 아니다(기술 35 · 기술+기본 71) |
| `estimated_total` | **완전 관측이 아니고** 축마다 관측이 하나라도 있을 때 | 결측을 축 비율로 보정한 추정치 (프로필 만점 기준). 완전 관측이면 원점수와 같으므로 비운다 |
| `total` | **완전 관측 + 100점 공통 프로필에서만** | 확정 총점 (최대 100) |

중간 프로필에서도 점수 열이 비지 않도록 `raw_total`·`estimated_total`을 채운다. 다만 `total`은 공시·수급·뉴스까지 들어온 100점 공통에서만 채워 척도가 다른 값이 한 열에 섞이지 않게 한다.

완전 관측일 때만 확정 `total`을 저장한다. 부분 관측은 `total=null`과 별도 `estimated_total`을 사용한다. 전체/축 하한 미달은 `insufficient_data`, 분류상 비대상은 `excluded`다. 위험 사유에 따른 랭킹 제외는 별도 `rank_eligible=false`로 표현해 계산 가능 여부와 구분한다.

### 4.4 등급·위험·스크리닝 — F8, F9, F19

- A/B/C/D 초기 실험 컷은 100점 척도의 75/60/45다(환산하지 않는다). 검증을 통과한 규칙 버전만 확정 등급을 게시한다. 잠정·제외·자료 부족·중대 위험은 `grade=null` 및 사유를 표시한다.
- `pct_rank`는 동일 게시본·프로필·자격 집단에서 계산한다. 전체/시장/업종을 구분하고 표본 수를 표시한다. 동점은 평균 순위, 화면의 안정 정렬은 점수 내림차순 후 ticker 오름차순이다.
- `fatal`, 자본잠식, 판단일 거래정지 등은 총점과 별도의 `risk_flags`다. 중대 사건 검토가 필요한 종목은 일반 랭킹에서 제외한다. 제목 기반 의심 사건을 확정 법적 사실로 표현하지 않는다.
- 30일 공시 창에서 사라졌다는 이유만으로 미해결 중대 위험을 해제하지 않는다. 해제 근거·시각을 별도로 보존한다.
- `passes_screen`: 기술 점수 21/35 이상 + D의 SMA5>SMA20>SMA60. 기술 입력·이동평균이 모두 유효할 때만 true/false, 그 외 null이다. 잠정 정규화로 통과시키지 않는다.
- alerts의 `종가>MA20>MA60` 전환 신호와 집합이 다른 것이 정상이다. 스크리닝은 점수 산출 범위를 줄이지 않는다. 선택 뉴스 조회를 결정할 수 있으나 뉴스는 공통 점수에 영향을 주지 않는다.

## 5. 입력과 계산 계약

### 5.1 거래일·기준시각

| 필드 | 정의 |
|---|---|
| `data_date` | 평가 대상 거래일 T. 실행한 달력 날짜와 다를 수 있음 |
| `information_cutoff_at` | 해당 실행에서 허용한 정보의 마감시각, UTC 저장·KST 표시 |
| `first_seen_at / fetched_at` | 최초 관측 / 이번 조회 시각 |
| `published_at` | 검증 후 실제 공개된 시각 |
| `source_run_id / source_snapshot_id` | 수집 실행·입력 버전 식별자 |

`Asia/Seoul`을 명시한다. 지수의 날짜 집합은 보조 달력이다. 지수도 누락될 수 있으므로 독립된 KRX 거래일/휴장일 정보와 대조한다. 평일·빈 응답만으로 휴장을 판정하지 않는다. 자정이 넘어도 T는 자동으로 바뀌지 않는다.

일봉 입력은 반드시 `d <= data_date`로 제한한다. 공시·재무·뉴스는 정보 마감시각까지 알려진 입력만 쓴다. 날짜만 있는 과거 공시는 보수적으로 다음 거래일 적용하는 정책을 사용하며, 실제 시각이 확인되는 운영 스냅샷과 구분한다.

### 5.2 기술 — F2

**상위 `ksc_bars`의 W/M은 채점에 사용하지 않는다.** 필요한 D OHLCV를 읽어 순수 함수로 W/M을 직접 계산한다. 기존 `resample.py`를 재사용할 때도 날짜 상한·고정 기간 키·완성 여부 계약을 새로 검증한다.

- 논리 키: `(ticker, timeframe, period_start)`. `last_trading_date`와 `is_complete`는 별도 값이다.
- 주는 월요일 시작 달력 주, 월은 달력 월로 그룹화한다. 거래소 달력으로 해당 기간의 마지막 거래일을 판단한다.
- 기본 채점은 **T까지 완성된 W/M만** 사용한다. 진행 중인 주·월은 상세 참고 정보로만 노출한다. 금요일 휴장 등도 거래일 달력으로 완성 여부를 판단한다.
- 집계는 첫 시가·최고 고가·최저 저가·마지막 종가·거래량 합이다. 동일 주/월 일봉을 여러 번 처리해도 기간당 한 행이어야 한다.
- 가격·거래량의 수정 기준과 추출 시각을 기록한다. 수정주가 재백필 실패가 확인된 종목은 기술 계산을 보류한다.
  **해석 주의(2026-09-20 확인):** 상위 `ksc_meta.drift.drifted`는 「그날 소급 변경이 발견돼 **재백필한** 종목」이며 낡은 종목 목록이 아니다(상위 `run_check_drift`가 즉시 3년치를 다시 받는다). 따라서 `failed = 0`이면 보류하지 않는다. `failed > 0`이면 상위가 실패 **개수**만 남겨 어느 종목인지 알 수 없으므로, 그 실행에서는 목록 전체를 보수적으로 보류하고 `drift_unresolved`를 기록한다. 실패 종목 목록을 남기도록 상위에 요청하는 것은 별도 변경이다.
- 정배열 MA는 SMA. RSI와 MACD의 평활법·시드·워밍업은 SMA와 별개로 규칙에 명시한다. 3년 일봉으로 월봉 MA120을 계산할 수 있다고 가정하지 않는다.
- 거래정지 의심일은 `v=0`와 OHLC 보합 등으로 표지하되 공식 상태·데이터 오류와 구분한다. 원본 날짜 행은 보존한다. 거래량 비율에서 제외하는 정책과 가격 지표의 유효 관측 수를 각각 기록한다.
- 시장 최근 20거래일 창을 종목의 과거 20개 유효 행으로 조용히 늘리지 않는다. 유효 관측이 모자라면 항목이 결측이다.
- 가격대별 거래량은 OHLCV 기반 **근사치**다. 실제 호가·체결 매물대라고 표현하지 않는다. 대표 가격·구간 수·창·배분법은 D4에서 고정한다.
- 거래대금 `a`가 NULL이면 원본을 덮어쓰지 않는다. `(h+l)/2*v`는 별도 `estimated_turnover`로만 보관하며, 정확한 거래대금이 필요한 기본 수급 점수의 분모로 자동 대체하지 않는다.

### 5.3 재무·업종 — F3

재사용 범위는 DART 요청, 계정 정규화, 연결 우선, 보고서 후보 탐색, 예외 처리다. 비율 계산과 점수 함수는 별도 구현이다.

**v2.5 개정 (2026-09-20, 사용자 결정): 여섯 항목 모두 최신 정기보고서(2026-09 기준 반기보고서)에서 직접 계산한다.** KRX가 공표하는 PER·PBR은 **직전 사업연도(2025년 말) 이익·자본** 기준이라 실적이 바뀐 종목에서 크게 어긋난다(2026-09-19 실측: 삼성전자 KRX PER 39.52 → 반기 기준 6.39, SK하이닉스 29.93 → 5.03). pykrx 지표는 점수에 쓰지 않는다.

**이익은 최근 4분기 합산(TTM)이다 (v2.6, 네이버 정의 채택).**

```text
TTM 순이익 = 직전 사업연도 당기순이익 + 당기 누적 − 전년 동기 누적
             (최신 보고서가 사업보고서면 그 값 자체)
주식 수    = 보통주 상장주식수 + 같은 회사 우선주 상장주식수
EPS        = TTM 순이익 ÷ 주식 수
BPS        = 최신 보고서 자본총계 ÷ 주식 수
```

- **보통주와 우선주를 합산한다.** 우선주는 DART corp_code에 없으므로 **티커 앞 5자리**로 묶는다 — 2026-09-20 실측에서 우선주 114개가 모두 보통주와 짝이 맞았다(삼성전자 58.5억 + 8.0억 = 66.5억 주).
- 우리가 가진 것은 **상장주식수**이며 네이버가 쓰는 수정평균발행주식수·수정기말유통주식수(자기주식 제외)가 아니다. 차이를 근거에 `shares_basis=listed`로 남긴다.
- 전년 동기 누적이 없거나 기간이 맞지 않아 TTM을 만들 수 없으면, 누적을 12개월로 연환산(반기 ×2 · 1분기 ×4 · 3분기 ×4/3)해 쓰고 `basis=annualized`로 표시한다. 둘 다 불가하면 결측이다.

| 지표 | v2.5 계산 계약 |
|---|---|
| PER | **T일 보통주 종가 ÷ EPS**(위 산식). TTM 순이익 ≤ 0이면 `adverse_defined`(0점). 같은 시장·업종의 **유효 양수 표본** 중앙값과 비교하며, 중앙값도 같은 방식으로 계산한 값으로 만든다. 표본 5 미만이면 시장 중앙값 폴백 — 폴백·표본 수 기록 |
| PBR | **T일 보통주 종가 ÷ BPS**(위 산식). 자본총계 ≤ 0이면 `adverse_defined` + `capital_impairment` |
| 영업이익률 | 같은 누적 기간의 영업이익 ÷ 매출액 ×100. 매출액>0 필요 |
| 배당수익률 | **KRX 공표값(pykrx `DIV`)을 그대로 사용**(v2.7). 근거에 `DPS`와 기준을 남긴다. 무배당 0%는 관측이며 결측이 아니다. 리츠는 12개월 연환산 값임을 표시 |
| 성장률 | **누적 매출액·누적 영업이익의 전년 동기 대비 증가율**(4+3점, §4.5). 같은 회계기간·길이·연결 기준으로 비교. 전년 값≤0이면 임의 증가율 생성 금지 |
| ROE | **TTM 순이익 ÷ 평균 자본**(직전 결산 자본총계와 당기말 자본총계의 평균) ×100. v2.4까지의 「연간 사업보고서만·분기 연환산 금지」는 이 결정으로 대체됐다 — 최신 반기 실적을 반영하기 위함이다. 지배주주 기준과 혼합하지 않는다 |
| 부채비율 | 같은 결산일 부채총계 ÷ 자본총계 ×100. 자본≤0은 불리한 상태·위험 표지로 처리 |

주식 수는 상위 `ksc_tickers`의 당일 값(`list_shrs`·`mktcap_d`)을 우선주까지 합산한 것이다. **과거 T를 다시 계산하면 그 시점이 아니라 현재 주식 수를 쓰게 되므로**, 근거에 `shares_as_of`를 남기고 소급 검증에서 한계를 표시한다(§7.3).

성장률은 원본대로 매출과 영업이익 두 하위항목이다(v2.0의 "대상이 비어 있었다"는 기술은 오류였다). 다른 성장 지표를 채택하려면 규칙 버전을 바꾼다. 금융·보험·리츠에 제조업의 부채비율·매출 개념을 그대로 적용하지 않는다.

재무 입력 보존 항목: corp_code, 사업연도, 보고서 코드, 접수번호, 접수일, CFS/OFS, IS/BS, 계정명/정규화명, 통화·단위, 실제 금액 열, 기간 시작·끝, 원본 해시. `thstrm_add_amount` 등 누적 열은 기간을 검증한 뒤 사용한다. `frmtrm_amount`를 무조건 전년 같은 분기라고 간주하지 않으며, 비교 기간이 다르면 전년 같은 보고서를 별도로 확보한다. [OpenDART 주요계정 명세](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS003&apiId=2019017)

CFS를 우선하며 비율의 분자·분모·비교기간 안에서 OFS와 섞지 않는다. 폴백 보고서와 회사별 결산월을 기록한다. 보고서 하강 탐색은 해당 시점에 실제 접수된 후보만 대상으로 하며, 최대 노후도 초과·반영 지연은 결측 사유로 남긴다.

다중회사 청크는 기존 검증값 15개로 시작할 수 있다. 공식 오류 안내의 최대 100개를 근거로 즉시 100개 완전 응답을 보장하지 않는다. 청크별 요청 회사/응답 회사·필수 계정·오류 코드를 검사하고 실측 후 증량한다. 한 후보·한 청크의 호출 수와 전체 탐색 비용을 구분한다.

### 5.4 수급·공매도 — F5

- 수급 단위는 원화 순매수 거래대금이다. 외국인은 `foreign_net + foreign_etc_net`, 기관은 `inst_net`이다.
- **NULL 해석 (v2.2 변경):** 상위는 투자자별 표에 종목이 없으면 NULL로 둔다. 투자자 5부류(기관·외국인·기타외국인·개인·기타법인) 순매수 합은 0이므로, **같은 행에서 NULL이 아닌 값의 합이 0이면 NULL을 0으로 확정**하고 근거에 `derived_zero`를 남긴다(state는 `observed`). 합이 0이 아니면 `missing(invalid_value)`이다. 행 자체가 없으면 0으로 만들지 않는다 — M0에서 행 없는 116종목은 전부 `v=0`(거래정지 의심)이었다.
  - 변경 사유: M0 항등식 검증(2026-08-18~09-18)에서 NULL 포함 28,627행 전부의 나머지 합이 0이었다. 기존 규칙대로면 외국인 6점이 약 28%, 기관 5점이 약 8% 종목에서 결측이 되어 기본 랭킹이 크게 줄어든다. 항등식이 깨지는 행이 생기면 그 행만 결측이 되므로 안전장치가 유지된다.
- 창은 독립 달력의 최근 5/20거래일이다. 누적 수급은 같은 기간의 실제 거래대금 합으로 규모를 보정한다. 단순 원화 금액으로 전 종목을 비교하지 않는다.
- 연속 순매수는 인접 거래일 자료가 모두 있을 때만 확정한다. NULL을 건너뛰어 긴 연속 기간을 만들지 않는다. 필요하면 `확인된 연속 일수 하한`을 참고 표시하되 완전 관측 점수와 구분한다.
- 공매도는 일별 `ratio`의 20거래일 산술평균이다. `short_vol / buy_vol`과 단위를 표본에서 확인한다. 분모 0·NULL·행 부재는 0%와 다르다. 20일 합계 비율로 바꾸려면 규칙 버전을 변경한다.
- 공매도 거래 비중은 잔고·미청산 포지션이 아니다. 낮을수록 높은 점수를 주는 방향과 시장별 경계값은 검증 가설이며 M2에서 확정한다.
- 정상 값 0은 관측이다. 출처 실패는 결측이며, 상위 메타의 저장 행 수만으로 NULL 없는 유효 관측 수를 대신하지 않는다.

### 5.5 공시·뉴스·사전 — F4, F10~F12

공시 수집은 날짜축으로 새로 구현한다. `corp_cls=Y`, `K`를 각각 조회하거나 전체 조회 후 명시적으로 필터링한다. 모든 공시를 수집하고, `pblntf_ty=A`는 재무 갱신 큐에 쓰는 분류다. 공시 점수 전체를 A 유형으로 한정하지 않는다.

페이지당 최대 100건, 회사 미지정 검색기간 최대 3개월 계약을 지키며 `total_page` 끝까지 읽는다. **이력 수집은 `last_reprt_at=N`**으로 원본·정정을 보존한다. Y는 최신 상태 보기용으로만 사용한다. 최신본만 받으면 과거 시점 재현에 필요한 정정 전 사건을 잃을 수 있다. [OpenDART 공시검색 명세](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001)

공시 점수 기본안은 최근 30달력일, 기본 4점, 독립 사건별 호재 +1.5·악재 -2, 0~7 제한, 유효 fatal 사건은 0 덮어쓰기다. 정정/철회 관계를 우선하며, 동일 회사·정규화 제목 중복 제한은 보조 규칙이다. 서로 다른 계약을 제목만 같다는 이유로 무조건 합치지 않는다. 모호하면 사건 분류를 보류한다.

**호재·치명 목록 확정 (v2.9, 2026-09-23 사용자 결정).** verify `flags.py`의 규칙표는 악재(🔴/🟡)만 담고 있어 호재와 치명을 새로 정했다.

| 구분 | 규칙 | 판정 키워드 (정규화 후) | 제외어 |
|---|---|---|---|
| 호재 +1.5 | `treasury_buy` | 자기주식취득결정 | 처분 · 해지 · 결과보고서 |
| | `treasury_trust` | 자기주식취득신탁계약체결결정 | 해지 |
| | `bonus_issue` | 무상증자결정 | 철회 |
| | `dividend` | 현금·현물배당결정 | 철회 |
| | `supply_contract` | 단일판매·공급계약체결 | 해지 · 해제 |
| 치명 → 0 | `delisting` | 상장폐지 | 해소 |
| | `rehabilitation` | 회생절차 | 종결 · 폐지 |
| | `embezzlement` | 횡령 · 배임 | — |
| | `audit` | 의견거절 · 범위제한 · 비적정 · 부적정 (note 포함) | — |

치명은 **강등 규칙을 거친 뒤 🔴로 남은 사건만**이다 — 자회사·종속회사 공시는 한 단계 내려가므로(verify D9) 모회사가 자회사 회생으로 0점이 되지 않는다. 악재 해소(관리종목 해제 등)는 호재로 세지 않는다. 지정된 적 없는 종목과 해제된 종목이 같은 점수를 받지 않게 하기 위함이다.

사전 스키마: `term, norm, polarity, weight, scope, exclude[], priority, on_note, enabled, note`.

**편집 원본은 리포의 TOML 파일이다** (v2.9, 2026-09-23 사용자 요청) — `rules/lexicon/news.toml`(뉴스 낱말)·`rules/lexicon/disclosure.toml`(공시 규칙표). 코드 상수로 두면 검토도 편집도 할 수 없어서 파일로 뺐다. 선언 순서가 곧 우선순위이며, 배치는 시작할 때 파일을 읽어 해시로 버전을 고정하고 `kss_lexicon_versions`에 스냅샷한다. 파일을 고치면 **다음 실행부터** 적용되고 이미 게시된 점수는 그대로 남는다. 공시 규칙을 더하면 `tests/test_flags.py`의 양성·음성 표본도 함께 넣어야 한다 — 표본 없는 규칙은 테스트가 막는다.

사전이 놓친 것을 눈으로 보려면 `scripts/m3_news_review.py`가 게시본에서 **중립으로 빠진 제목**을 `docs/m3/news_review_<T>.md`(검토용)와 `docs/m3/news_labels_<T>.toml`(D7 라벨링 원본)로 낸다. 공시 위험 규칙에는 `fatal` 및 강등/예외 로직을 별도로 둔다. verify `flags.py`의 위험 등급표는 공시 시드의 재료이며 긍정·부정 뉴스 사전 자체가 아니다. 자회사·리츠 강등 규칙도 테스트와 함께 재사용한다.

**v2.5 개정: 뉴스는 공통 점수 9점이며 전 종목을 매일 조회한다**(사용자 결정, 2026-09-20). 종목마다 관련 기사 **최대 3건**을 골라 사전으로 호재 +3 · 악재 −3 · 중립 0을 매기고 합산한다(−9 ~ +9). 기사가 3건 미만이면 있는 만큼만 더한다.

- 조회 범위: 전 종목(약 2,585회/일 — 네이버 한도 25,000회의 10%).
- 기사 선정: 최근 7일, 회사 관련성 필터를 통과한 기사 중 최신 3건. 제목·링크·발행시각·선정 근거를 저장한다.
- 상태: 미조회 `not_queried`, 요청 실패 `source_error`, **완전 조회 후 기사 없음은 `no_event`(0점)**. 셋을 섞지 않는다.
- **창의 끝은 T의 자정이 아니라 `information_cutoff_at`(실행 시각)이다**(v2.9, 2026-09-23 실측). 네이버 검색에는 날짜 조건이 없고 최신순 20건만 오는데, 활발한 종목은 그 20건이 모두 당일 기사다 — T 자정으로 자르면 전 종목이 `no_event`가 된다(실측: 4종목 모두 `fetched 20 · in_window 0`). 공시·재무와 같은 규칙이다(§5.1).
- **소급 실행에서는 뉴스를 만들지 않는다.** T가 실행일보다 `news.max_lag_days`(기본 3일)보다 더 오래되면 그 시점 기사를 받을 방법이 없으므로 `not_queried`로 남긴다 — 오늘 기사로 과거 점수를 만들지 않는다.
- 사전 검증(D7) 전에는 `experimental`로 두고, 뉴스가 들어간 총점을 확정 등급으로 게시하지 않는다.

검색어·회사 별칭·관련성 필터·HTML 제거·URL/제목 중복 제거·검색 기간·수집 상한·절단 여부·시각을 보존한다. 이름이 짧은 회사는 별칭·문맥 확인을 강화하고 불명확한 기사를 제외한다. 단지 두 글자라는 이유로 회사의 모든 기사를 결측 처리하지 않는다. 표본 제목 300건 내외를 별도로 라벨링해 정밀도·오분류·중립어 문제를 평가하고 사용 여부를 결정한다.

활성 사전은 불변 버전으로 스냅샷한다. 한 배치가 시작되면 사전·규칙 버전을 고정한다. 사전 편집은 이후 새 실행에 적용하며 기존 게시 점수를 소급 덮어쓰지 않는다.

## 6. 수집 완료·배치·복구 — F13, F14, F17

### 6.1 트리거와 시간

기본 방향은 **charts 수집 완료 후 `repository_dispatch`**다(v2.2: **M4에서 연결** — M0 실측에서 charts 예약 18:00이 실제 22:00~익일 01:30에 시작했다). payload에는 원본 run ID·commit SHA·대상 거래일을 넣고, 수신자가 실제 원본 실행·DB 상태를 재검증한다. 이벤트가 왔다는 사실 자체는 품질 통과가 아니다.

상위 workflow 수정이 필요한 이벤트 연동은 D2 범위다. 그 전에는 scoring 리포만으로 실행 가능한 **23:37 KST(UTC 14:37) 평일 잡 + 매일 07:17 KST(전일 UTC 22:17) 복구 잡**을 기본 대안으로 둔다. 아래 UTC 표현은 요일 착오를 피하기 위한 예시다.

```yaml
schedule:
  - cron: '37 14 * * 1-5'  # 월~금 23:37 KST, 주 채점/미게시 대상 확인
  - cron: '17 22 * * *'    # 매일 07:17 KST, 거래일 달력으로 누락 재확인
```

Actions 예약은 지연·누락될 수 있다. 짧은 폴링은 이미 끝나가는 수집을 기다리는 보조 수단으로만 쓴다. 기본 브랜치의 `repository_dispatch / workflow_dispatch / schedule`과 제한된 복구 큐를 함께 둔다. 다른 리포의 `workflow_run`이 자동 연결된다고 가정하지 않는다. 이벤트 수신 workflow가 기본 브랜치에 있어야 한다. [GitHub 이벤트 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#repository_dispatch)

이벤트 전송은 대상 리포에 한정된 GitHub App 토큰 또는 fine-grained PAT를 사용한다. 저장소 간 전송 권한·토큰 만료·실패 재시도를 확인하며, 단순히 기본 `GITHUB_TOKEN`이 다른 리포를 호출할 수 있다고 가정하지 않는다.

다음 날 아침까지 T일 점수를 제공하는 것을 운영 목표로 둔다. 공개 시각을 보장하지는 않으며 웹에 `T일 자료 / 실제 갱신시각 / 지연 사유`를 표시한다. 화면에 날짜 없는 “오늘 점수”를 쓰지 않는다.

### 6.2 입력 준비와 채점의 분리

1. 입력 준비 작업: corp_code 매핑(주 1회+신규 종목), 날짜축 공시(매일+겹치는 기간 재조회), 신규·정정 정기보고서 재무 갱신, pykrx 시장별 지표 캐시.
2. 채점 작업: T 결정 → 상위 품질 검사 → 유니버스/입력 스냅샷 고정 → D 기반 기술 → 기본·공시·수급 → 합산·자격 → 검증 → 게시.
3. 선택 뉴스 작업: 공통 점수와 분리하여 보조 정보 갱신. 뉴스 장애가 공통 랭킹 게시를 막지 않는다.
4. 후속 대조 작업: 최근 미연결 alerts 신호를 같은 기준일의 게시본과 연결한다.

입력 준비를 아침에 수행했더라도 T일 정보 마감까지 신규 정기보고서·정정이 있는지 채점 전 확인한다. 새 보고서 반영이 늦으면 예전 자료를 최신으로 위장하지 않고 `financial_pending` 및 날짜를 표시한다. 필수 항목 신선도 조건을 못 채우면 잠정/보류한다.

### 6.3 출처별 품질 게이트

각 출처·시장·T마다 `expected_count, stored_count, valid_count, null_count, duplicate_count, min/max_date, coverage, observed_at, status, reason`을 남긴다. `expected_count`는 해당 출처가 제공해야 할 대상 집합이며, 구조적 비대상을 구분한다.

| 입력 | 검사 | 실패 처리 |
|---|---|---|
| 거래일·유니버스 | 독립 거래일, 분류 신선도, 신규/제외/정지 사유 | 해석 불가 시 T 게시 차단 |
| 일봉 D | 시장별 대상·유효 OHLCV·기간 연속성·날짜 상한·수정 이력 | 시장 전체 장애면 게시 차단, 일부 종목은 명시적 보류 |
| 수급/공매도 | `ksc_meta.update` 갈래별 행 수 + 실제 T 행·NULL·20일 관측 | 해당 항목 결측. 정상 전체 실행으로 표시하지 않음 |
| 업종·PER/PBR | 업종 갱신일, 지표 기준일, 유효 표본, 시장 폴백률 | 폴백/노후 표지, 허용 한도 초과면 보류 |
| 공시·재무 | 페이지 완주, 접수/정정 처리, 보고서·기간·최대 노후도 | 출처 오류와 실제 사건 없음 분리 |

`ksc_meta`의 update 값은 최신 상태 힌트이며 실패 이력 전체가 아니다. `tradingDay=false`도 독립 달력으로 대조한다. `updated_at`은 행 수정 시각, `updated` 등 JSON 값은 실제 스키마에서 의미를 검증한다. 워크플로 success와 MAX(d) 하나로 게이트를 통과시키지 않는다.

초기 운영 검증값은 시장별 D 유효 커버리지 99%, 수급/공매도 95%다. 분모와 구조적 비대상을 실측한 뒤 D3에서 확정한다. 이 값 이상이어도 개별 누락을 0으로 보정하지 않는다. 일부 부족을 게시할 때는 `published_degraded`, 대상 수·보류 수·누락률을 공개하고, 시장 단위 장애나 기준 미달이면 이전 게시본을 유지한다.

### 6.4 상태·재시도·게시

- 실행 시작 시 `kss_runs`에 먼저 기록: `created → checking → computing → validating → published / published_degraded`. 종료 대안은 `waiting_upstream / no_trading / failed / cancelled`다.
- `waiting_upstream`은 완료가 아니다. 같은 T를 복구 큐에 남긴다. 기본 자동 복구 범위는 최근 5거래일, 그 이전은 명시한 날짜 범위의 수동 재처리다.
- 이 큐는 **점수 미게시** 복구용이다. 상위 D 누락까지 scoring이 자동으로 고치지는 않는다. 상위 누락은 해당 리포 복구 요청 대상으로 기록한다.
- 동일한 T·프로필에 중복 이벤트가 와도 잠금/멱등성 키로 중복 게시를 막는다. 진행 중인 정상 실행을 새 이벤트로 취소하지 않는다.
- 실행 내 청크 재시도는 같은 run ID에서 멱등 처리한다. 입력·사전·규칙이 달라지는 재평가는 새 run ID를 만든다. 강제 종료는 heartbeat 만료로 감지한다.
- 점수 저장 중간 실패 시 기존 게시본을 유지한다. 모든 행·합계·유니버스·버전·품질 검증 후 한 트랜잭션에서 게시 포인터를 변경한다.
- 30분은 정상 채점의 목표 시간이며 GitHub 강제 상한이라는 표현을 쓰지 않는다. 자체 timeout은 초기 60분을 후보로 실측하고, 대량 초기화·아카이브는 별도 잡으로 분리한다.

## 7. 저장·재현·비용 — F7, F15, F18

### 7.1 저장소 방향과 선행 조건

**확정(2026-09-19, D1 — v2.2 재결정): kss 전용 Supabase 무료 프로젝트 + Parquet 아카이브.** 비용 0을 유지한다.

- 재결정 사유: M0 실측에서 공유 DB가 **513 MB로 무료 한도 500 MB를 이미 넘었다**(`ksc_bars` 350 MB). 공유 DB에는 게시본만 두는 안도 들어갈 자리가 없다.
- **상위 입력**은 지금처럼 공유 DB의 `ksc_* / ksa_*`를 읽기만 한다(연결 2개: 상위 읽기용 · kss 쓰기용).
- **kss DB(전용 프로젝트, `kss_` 접두어 유지)**: 실행·게시 포인터·게시본 요약(초기 목표 120거래일)·항목 근거(초기 목표 최근 10거래일)·사전·위험 사건·품질 기록. 웹은 이 DB만 읽는다. 사용량 경고 400 MB, 신규 상세 저장 중단 450 MB(초기값, M1 실측 후 확정).
- **아카이브(Parquet)**: 입력 스냅샷·오래된 상세 근거·불변 재무/공시 버전의 장기 사본. 영속 위치는 깃허브 Release 자산을 1안으로 PLAN에서 확정한다(Actions artifact·러너 디스크는 장기 보존소가 아니다).
- 보존 기간·용량 경고·게시 중단 기준은 **M0 실측(하루 전 종목 저장량) 뒤** 숫자로 고정한다. 공유 DB 잔여가 예산에 못 미치면 상세 보존을 줄이며, 그래도 부족하면 전용 프로젝트·유료 전환을 다시 결정한다.
- 전용 DB여도 `kss_*`는 anon 정책 없이 RLS를 켠다. 전용 프로젝트의 anon 키는 웹에 쓰지 않는다(서버 사이드 `kss_reader`).
- 공유 DB의 한도 초과 자체(다른 프로젝트 전체에 영향)는 scoring 범위 밖이며 별도 조치 대상이다.

선택 전 마이그레이션·과금 변경·대규모 백필을 실행하지 않는다.

### 7.3 재현성의 수준

- 운영 시점 재현: 당시 입력 스냅샷·규칙·사전·코드·라이브러리 버전으로 재계산한다. 같은 입력이면 반올림·동점 정렬까지 같아야 한다.
- 재무 원문은 매일 모든 종목 점수에 복제하지 않고 불변 버전을 참조한다. 기술 입력은 특징값과 원천 자료 hash/아카이브를 연결한다.
- `parts.actual`만으로는 당시 없던 원문·정정 전 입력·유니버스를 복원하지 못한다. 숫자 재계산과 출처 검증을 모두 하려면 참조 원본을 보존해야 한다.
- 현재 API로 과거 날짜를 재조회한 값은 `recomputed_with_current_data`로 구분한다. 접수번호나 과거 관측시점을 지정할 수 없는 API만으로 완전한 당시 시점 복원을 보장하지 않는다.
- 입력을 찾을 수 없는 기간·축은 검증 범위에서 제외한다. 현재 상장 종목·현재 업종만 사용한 소급 분석은 생존·분류 편향을 명시한다.

### 7.4 보존·예산

**확정 보존(v2.4, 2026-09-19 M1 실측 후 사용자 결정): 게시 점수 요약 252거래일 · 항목 근거 3거래일 · 유니버스 스냅샷 20거래일**, 그 이전 근거·스냅샷과 입력/불변 버전은 압축 아카이브(M4). 실측(기술 5항목 프로필): 하루 점수 ~1.2 MB · 근거 ~5 MB · 유니버스 ~0.5 MB. 근거가 15항목이 되면 ~15 MB/일로 추정한다. M2 첫 `common` 실행에서 행 크기를 다시 재고, 정상 상태 예상이 경고선(400 MB)을 넘으면 점수 행의 중복 열 축소·`technical` 프로필 중단으로 맞춘다. 오래된 근거도 보존 기간 안에는 아카이브에서 복원할 수 있어야 한다. 삭제 전 manifest·hash·복원 검증을 통과해야 하며, 참조 중인 버전·현재 게시본은 제거하지 않는다. **미해결 위험은 삭제 조건이 아니라 대상에서 빼는 것으로 지킨다**(v2.9 정정) — 위험 사건과 근거 공시는 `kss_risk_events`·`kss_disclosures`에 있고 애초에 삭제 대상이 아니다. 이를 실행 단위 조건으로 적었더니 미해결 위험이 있는 종목이 하나라도 든 실행이 전부 막혀 아무것도 지워지지 않았다(2026-09-23 실측, 827건).

아카이브는 `jsonl / parquet` 등 이전 가능한 형식으로 보관한다. **M4에서 `jsonl.gz`로 확정했다**(2026-09-23) — 표준 라이브러리로 읽고 쓰므로 새 의존성(pyarrow)이 없고, DuckDB가 `read_json_auto`로 그대로 읽는다. 파일은 `mtime=0`·파일명 헤더 없이 써서 **같은 내용이면 바이트까지 같다**. 삭제 순서는 짧게 보존하는 것부터다(근거 → 유니버스 → 점수) — 점수를 먼저 지우면 근거가 FK로 딸려 가 삭제 수가 0으로 보고된다(실측). 장기 소급 분석은 로컬 DuckDB/Parquet를 기본으로 한다. Actions 러너의 임시 디스크나 만료되는 artifact만을 장기 보존소로 삼지 않는다. 영속 저장 위치·비용·백업 책임은 D1에 포함한다.

```text
일 증가량 ≈ 당일 종목 수 × 평균 행/상세 크기 × 보존할 실행 버전 수
전체 사용량 = 점수 + 근거 + 인덱스 + 원본/스냅샷 + 실행/게시 이력
```

예시로 2,770종목×252일은 약 69.8만 점수 행이며, 행당 5KB 가정만으로 연 약 3.49GB다. 실제 압축·인덱스·TOAST 크기는 별도 측정한다. 전용 무료 DB도 무제한 이력을 감당한다고 가정하지 않는다.

M0에서 수백 종목 표본과 하루 전 종목 저장량으로 일/월/연 증가량, DB 읽기량, 전송량, 아카이브 크기를 산정한다. 예상 보존량이 용량 예산을 넘으면 상세 기간을 줄이거나 저장소를 변경한다. 용량 경고·신규 게시 중단 기준은 계정 할당량에 맞춰 D1에서 정한다.

| 경로 | 예산 산정 |
|---|---|
| 기술·수급 | 외부 시세 API 추가 0회. DB 읽기·집계·전송 비용은 존재 |
| PER/PBR | 기본 시장별 날짜축 요청, 실패 재시도 별도 |
| 재무 | `ceil(고유 회사 수 / 청크) × 필요한 후보 수 + 정정/재시도` |
| 공시 | 두 시장·각 날짜 범위의 실제 전체 페이지 수 |
| 뉴스 | 선택 조회 종목 수·페이지·재시도, 공통 점수와 분리 |

정상일·실적 집중일·빈 캐시·재시도 시나리오의 p50/p95·최대 시간을 기록한다. 기존의 “평일 200회 미만/30분 넉넉”은 보장으로 사용하지 않는다.

## 8. alerts 대조 — F16, F23

`ksa_signals.d`는 실행일이 아니라 입력 봉의 기준일이다. **signal.d = score.data_date**로 연결한다. 달력상 D-1을 무조건 빼지 않고 실제 거래일을 사용한다.

T일 점수가 야간에 게시되고 T+1 아침 alerts가 T일 신호를 만들면, 후속 작업에서 T일 점수와 연결한다. 07:17 복구 시각보다 신호가 늦게 생성될 수도 있으므로 다음 실행마다 최근 10거래일의 미연결 신호를 보충한다. 필요하면 조회 시 조인한다.

비교 모드:

- `same_data_date`: 같은 기준 거래일 점수와 신호의 사후 대조.
- `available_at_signal`: 위 조건에 더해 `score.published_at <= signal.created_at/run_at`을 만족한 게시 이력을 선택. 당시 점수가 없었으면 없음으로 기록한다.

`rank_no`, `suppressed`, 전략명, score_run_id, 두 기준시각을 보존한다. 전략별 `ksa_signals.score`를 서로 같은 척도로 정렬하지 않는다. 신호 생성 후 사전 수정으로 재평가된 점수를 당시 이용 가능 점수로 보여주지 않는다.

주봉 기반 alerts는 상위 W 중복의 영향을 받을 수 있으므로 `upstream_weekly_quality_unverified` 표지를 둔다. 상위 검증 전 해당 대조를 점수 모델의 타당성 증거로 사용하지 않는다. M1의 기술 전용 대조는 `partial_technical`이며 완성 총점·등급을 만들지 않는다.

서버 역할의 상세 범위:

- 상위 DB: 전용 입력 읽기 자격증명. 상위 쓰기 가능한 service_role을 상시 공용 자격증명으로 쓰지 않는다.
- kss DB: `kss_batch`는 입력/점수/실행/게시 데이터의 필요한 쓰기만, `kss_reader`는 게시 뷰만, `kss_editor`는 제한된 편집·버전 생성 절차만.
- 스키마/RLS: 모든 kss 테이블에서 비인증 접근을 차단한다. 서버 역할도 필요한 GRANT/RLS/뷰 권한을 명시한다. RLS를 우회하는 역할을 읽기 전용이라고 부르지 않는다.
- 사전 변경: 인증, Origin/CSRF 확인, 입력 검증, 감사 이력, optimistic locking. 브라우저에 DB 비밀번호·배치 키를 전달하지 않는다.

배치는 Python·검증된 파서/계산 함수·psycopg를 기본 후보로 한다. 웹은 기존 verify의 서버 DB 접근 패턴을 재사용한다. **배치 실행기는 LangGraph를 얇은 그래프 층으로 쓴다(v2.3)** — verify N4와 같이 그래프 모듈만 LangGraph를 알고, domain·store는 LangGraph 없이 테스트된다. 그래프 상태에는 run_id·스냅샷 참조·집계 요약만 싣고 시세 행·항목 근거 같은 대량 데이터는 싣지 않는다. 멱등성·복구·원자적 게시는 그래프 체크포인트가 아니라 DB 트랜잭션·`kss_runs`가 책임진다. 실제 패키지·버전은 PLAN에서 기존 프로젝트 호환성을 확인해 고정한다.

DB의 전체 시계열은 종목별 REST 수천 호출 대신 필요한 열/기간을 배치 조회한다. REST 행 수 제한과 URL 길이 한계를 피하고, 커서/청크/청크별 검증을 둔다. 러너에서 가능한 IPv4 세션 풀러를 검증하며, 트랜잭션 풀러를 쓸 때는 prepared statement 설정을 명시한다. 연결 자격증명은 역할/DB별로 분리한다.

| 버전 | 같은 T의 두 사전/규칙 실행이 공존하고 각각 재현 가능 |
| alerts | T+1 생성된 d=T 신호 연결, 신호 시점 이후 게시 점수의 당시 비교 차단 |
| 용량·보존 | 하루 실측·보존 예측·아카이브 복원 성공. 과거 원본 참조가 끊어지지 않음 |
| 권한 | 상위 쓰기·비인증 읽기·비인증 사전 변경 차단, 정당한 경로는 성공 |

핵심 계산의 골든 테스트는 독립 계산값을 적는다. 코드 상수를 그대로 읽어 같은 상수와 비교하는 테스트로 배점 변이를 검출했다고 주장하지 않는다. 문서만 개정하는 이번 작업에 애플리케이션 테스트 실행을 완료했다고 기록하지 않는다.

### 11.2 점수 검증 범위

기술은 일봉이 확보된 최대 약 3년 범위, 재무·PER/PBR는 시점과 분류 입력이 확보된 구간, 수급·공매도는 실제 보존 구간만 평가한다. **120달력일을 120거래일로 늘려 쓰지 않는다.** 과거 뉴스 완전 재현은 출시 조건에서 제외한다. 전 축 3년 당시 재현을 약속하지 않는다.

순서: 계산 정확성 → 관측률/업종/규모/유동성 편향 → 항목 상관·제거 민감도 → 일일 순위 안정성 → 시간순으로 분리한 고정 평가구간의 초과수익 분포. 튜닝 구간과 평가 구간을 분리하며 겹치는 관측 기간을 독립 표본처럼 계산하지 않는다. 충분한 관측 전에는 연구 결과를 제품 확정 성능으로 표현하지 않는다.
